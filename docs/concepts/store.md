# Data Store

The data store is an in-memory data layer that manages rollouts, events, resources, and model servers. It runs in-process with the [gateway](gateway.md) — no network hop, no external database.

## Core entities

### Rollouts

A rollout represents a single task to be solved by an agent. It carries:

- **`input`** — the task description (delivered to the agent as `AGL_TASK_INPUT`)
- **`config`** — how to run it (container image, command, env vars, timeout, retries)
- **`resources_id`** — link to an immutable resource snapshot (job template, prompts, etc.)
- **`status`** — lifecycle state (see [state machine](#rollout-state-machine) below)

Rollouts are created by the algorithm (`POST /api/rollouts`) and managed by the [K8s controller](controller.md).

### Events

Events are the trajectory data — an ordered list per `(rollout_id, attempt_id)`. See [Data Model](data-model.md) for details on event types and trajectory structure.

### Resources

Immutable snapshots of experiment configuration. Each `POST /api/resources` creates a new snapshot with a generated ID. Rollouts reference a `resources_id` to pin their configuration.

The key resource for the controller is **`job_template`** — a raw K8s pod spec that defines how agent pods are configured. Other keys (prompts, eval configs) are user-defined and opaque to agl-lite.

### Model servers

Registered inference endpoints, grouped by model name. The gateway routes LLM requests to these servers. See [Gateway — Server selection](gateway.md#server-selection).

## Rollout state machine

```
queuing ──[controller creates Job]──→ running ──[Job Complete]──→ succeeded
   │                                    │                         (terminal)
   │                                    │
   ├──[Job creation failed]──→ terminal_failed ◄──[Job Failed]────┘
   │                           (terminal)
   │                                    │
   └──[cancel + no Job]──→ cancelled ◄──[cancel]─────────────────┘
                           (terminal)
```

**Valid transitions (store-enforced):**

| From | To | Trigger |
|------|----|---------|
| `queuing` | `running` | Controller: Job created |
| `queuing` | `terminal_failed` | Controller: Job creation failed |
| `queuing` | `cancelled` | Controller: `cancel_requested` set, no Job |
| `running` | `succeeded` | Controller: Job has `Complete` condition |
| `running` | `terminal_failed` | Controller: Job has `Failed` condition |
| `running` | `cancelled` | Controller: `cancel_requested` set, Job deleted |

Terminal states (`succeeded`, `terminal_failed`, `cancelled`) are final — the store rejects any further transitions.

### Cancellation

Cancellation uses a **flag-based** approach:

1. User sets `cancel_requested = true` via `POST /api/rollouts/{rid}/cancel`
2. Controller reads the flag during reconciliation
3. Controller deletes the K8s Job and sets status to `cancelled`

This separation of intent (flag) from execution (controller) avoids race conditions — the user doesn't need to know the current execution state.

## ID generation

| ID | Generated by | Mechanism |
|----|-------------|-----------|
| `rollout_id` | Store | UUID, created on `enqueue_rollout()` |
| `attempt_id` | K8s (implicitly) | Pod `metadata.uid` — unique per pod, exposed via Downward API |

On retry, K8s creates a new pod with a new UID. The attempt ID changes automatically — no custom ID generation needed. See [Controller — Attempt = Pod UID](controller.md#attempt-pod-uid).

## Attempt resolution

When querying events without specifying `attempt_id`, the store uses smart defaults:

1. If `rollout.succeeded_attempt_id` is set → use it
2. Otherwise → attempt with the earliest first event
3. No events exist → return empty

This means `GET /api/events?rollout_id=R1` returns the successful attempt's trajectory by default.

## Concurrency model

The store is **single-threaded by design**. All operations are synchronous in-memory dict/list mutations (nanoseconds). Called from `async def` route handlers on the asyncio event loop — completes instantly, never blocks.

No locks, no transactions. The partition key `(rollout_id, attempt_id)` eliminates cross-agent contention. Different agents never touch the same data partition.

## Data lifecycle

The store is in-memory — data grows with each iteration. The algorithm controls cleanup via the archive API:

```
POST /api/rollouts/archive
{
  "rollout_ids": ["r1", "r2", ...],
  "backend": {"type": "jsonl", "path": "/data/batch_42.jsonl"}
}
```

This persists rollouts + events to a JSONL file, then purges them from the store. Only terminal rollouts can be archived. Omit `backend` to discard without saving.

**Storage estimate:** 1,000 rollouts × 10 events × 5KB/event = 50MB per iteration. Archive after each iteration to keep the store bounded.
